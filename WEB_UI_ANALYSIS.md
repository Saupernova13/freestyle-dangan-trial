# Web UI Code Quality & Modernization Analysis

## Executive Summary

**Current State**: The web UI is **production-functional but architecturally fragile**. It works well for end-users but violates modern web development standards in nearly every dimension: no build system, no type safety, no linting, no testing, no module system, scattered global state, inline event handlers, and poor code organization. This is **"vibe coded"** — it got the job done quickly but will become increasingly painful to maintain and extend.

**Assessment Dimensions**:
| Dimension | Score | Status |
|-----------|-------|--------|
| Clean Architecture | 2/10 | Global state chaos, tight coupling, no separation of concerns |
| Self-Describing Code | 3/10 | Minimal inline comments, cryptic variable names, unclear intent in complex functions |
| Open Source Best Practices | 2/10 | No contributing guide, no linting, no type defs, no API documentation |
| Multi-Device Compatibility | 6/10 | Works on Chromium browsers, but CSS fragile, no responsive testing |
| SOLID Principles | 1/10 | Violates every principle; massive monolithic functions, tight coupling everywhere |
| Professional Standards | 2/10 | No CI/CD, no testing, no type checking, no error boundaries, no logging |

**Bottom Line**: The project needs fundamental restructuring to become maintainable at scale. A motivated team can add features, but refactoring will be painful. Every change risks breaking multiple unrelated systems because the code is coupled at the global level.

## Part 1: Current Architecture — The Vibe Coding Reality

### 1.1 Script Loading & Global Namespace Pollution

**Problem**: 22 global script tags with manual dependency ordering, everything exposed to global scope.

```html
<!-- index.html -->
<script src="js/core/constants.js"></script>
<script src="js/core/state.js"></script>
<script src="js/utils.js"></script>
<script src="js/ui/theme.js"></script>
<!-- ... 18 more files -->
```

**Issues**:
- No module system (ES modules disabled, CommonJS not available)
- Dependency ordering is fragile and undocumented
- Name collision risk (e.g., `renderScriptEditor`, `renderCharacterDropdown`, etc. all global)
- No tree-shaking or dead code elimination possible
- Impossible to parallelize loading
- No bundling = large browser cache footprint

**Real-world Impact**: Adding a new feature requires modifying HTML, updating 3-5 script files, and carefully managing what goes into `state.js` because there's nowhere else for it to go.

### 1.3 Event Handling: Inline HTML vs. Event Delegation

**Problem**: Mix of inline `onclick` attributes and scattered event listeners creates maintenance nightmare.

```javascript
// Inline handlers (in HTML generated by JavaScript)
<button onclick="deleteScriptLine('${line.id}')" title="Delete line">🗑️</button>
<button onclick="moveLineUp('${line.id}')" title="Move up">▲</button>
<input oninput="updateScriptLine('${line.id}', 'dialogue', this.value)" />
<input onfocus="openCharacterDropdown('${line.id}')" />

// But also scattered event listeners in JS files
document.addEventListener('click', function(e) { /* ... */ });
freshListEl.addEventListener('click', (e) => { /* ... */ });
```

**Issues**:
- Event handler names hardcoded in template strings → brittle, unsearchable
- No event delegation pattern (each element gets its own handler)
- Impossible to remove old event listeners; code leaks memory
- HTML-generation code mixed with event binding logic
- No way to handle nested/bubbling events cleanly
- Race conditions when re-rendering triggers event handler cloning:
  ```javascript
  // From app.js line 487-488 (memory leak!)
  const oldListEl = listEl.cloneNode(true);
  listEl.parentNode.replaceChild(oldListEl, listEl);  // Detaches all listeners
  ```

**Real Impact**: Character dropdown has to clone the entire DOM node and rebind listeners every time the list updates (inefficient, loses focus, loses scroll position).

## Part 2: Specific Code Quality Issues (Detailed)

### Issue 1: Memory Leaks in Event Delegation

**Location**: `app.js`, lines 487-511

```javascript
function attachDropdownEventHandlers(lineId) {
  const listEl = document.getElementById(`char-dropdown-list-${lineId}`);
  if (!listEl) return;

  // Remove old listeners if any
  const oldListEl = listEl.cloneNode(true);  // ❌ Clones node
  listEl.parentNode.replaceChild(oldListEl, listEl);  // ❌ Replaces in DOM
  const freshListEl = document.getElementById(`char-dropdown-list-${lineId}`);

  // Attach new listeners
  freshListEl.addEventListener('click', (e) => { /* ... */ });
  freshListEl.addEventListener('mouseover', (e) => { /* ... */ });
}
```

**Problem**: This function is called every time the dropdown list updates. It:
1. Clones the node (destroying all listeners)
2. Replaces it in DOM (causes re-flow)
3. Reattaches listeners

If the dropdown filters 10 times (user types 10 characters), listeners are attached/detached 10 times. This is O(n²) for typing.

**Fix**: Use event delegation on parent, not individual items.

## Part 3: SOLID Principles Violations

### Single Responsibility Principle ❌

Each file does too much:
- `app.js`: Script rendering, drag-and-drop, character dropdown management, modal coordination
- `storage.js`: File I/O, data loading, sprite caching, character loading
- `scriptLineModal.js`: Sprite UI, audio UI, highlighting UI, camera UI, effects UI, saving

---

### Open/Closed Principle ❌

Closed for extension: Adding a new line type requires:
1. Modifying `renderScriptLineBar()` in app.js
2. Modifying `changeScriptLineType()` in app.js
3. Modifying `autoSaveTrial()` in storage.js
4. Modifying `loadCharactersFromIds()` in storage.js

---

### Liskov Substitution Principle ❌

Not applicable (no type hierarchy), but would violate if implemented. Different line types (speaking, narrator, minigame) have incompatible fields but are stored in the same array without type discrimination.

---

### Interface Segregation Principle ❌

**Example**: The "character" object has fields for both student and headmaster:
```javascript
{
  id: "JD_...",
  name: "John",
  surname: "Doe",
  dateOfBirth: "1992-03-15",
  bloodType: "O+",
  height: 180,
  isHeadmaster: false,
  // Student fields only:
  schoolYear: 1,
  favorites: "...",
  talents: "...",
  // Headmaster fields only (if isHeadmaster):
  role: "Principal",
  // ...
}
```

Consumers must check `isHeadmaster` everywhere, or fields will be missing.

---

### Dependency Inversion Principle ❌

Everything depends on concrete global state, not abstractions:
```javascript
// Bad: depends on global cast, scriptLines, minigames
function renderCastView() { /* ... */ }

// Good (but not implemented): depends on abstraction
function renderCastView(state: TrialState) { /* ... */ }
```

## Part 6: Migration Strategy (Safe Incremental Path)

### Don't Rewrite Everything at Once ❌

**Risk**: Full rewrite takes months, creates merge conflicts, loses domain knowledge

### Instead: Incremental Migration ✅

**Strategy**: Keep old and new systems running in parallel

```typescript
// Phase 2: New state management alongside old globals

// old-system.js
let scriptLines = [];  // ← Keep for backward compatibility
let minigames = [];

// new-system.ts
const useTrialStore = create((set) => ({
  scriptLines: [],
  minigames: [],
}));

// adapter.ts (bridges old → new)
export function syncOldToNew() {
  const { setScriptLines, setMinigames } = useTrialStore.getState();
  setScriptLines(scriptLines);  // Copy from global
  setMinigames(minigames);
}

export function syncNewToOld() {
  const { scriptLines, minigames } = useTrialStore.getState();
  window.scriptLines = scriptLines;  // Copy to global
  window.minigames = minigames;
}
```

**Process**:
1. Week 1-2: Set up build, TypeScript, testing
2. Week 3: Create new state store alongside old globals
3. Week 4-6: Migrate one view at a time (castView → scriptEditor → minigameEditor)
4. Week 7-8: Replace DOM manipulation incrementally
5. Week 9-10: Add tests for migrated code
6. Week 11-12: CSS refactor with new system
7. Week 13-14: Remove old system entirely

**Rollback safety**: If new system breaks, revert to old code. No production disruption.

## Part 8: Risk Assessment & Mitigation

### Risks of Not Modernizing

| Risk | Impact | Probability |
|------|--------|-------------|
| Developer velocity decreases | Features take 3x longer | High |
| Data corruption from bugs | User loses trial data | Medium |
| Performance degrades | App unusable with 100+ lines | High |
| New contributors frustrated | No one wants to maintain it | High |
| Refactoring becomes impossible | Technical debt accumulates | High |

### Risks of Modernizing

| Risk | Mitigation |
|------|------------|
| Rewrite takes too long | Use incremental migration (parallel systems) |
| New system has bugs | Comprehensive test coverage before removal of old code |
| Team unfamiliar with tech | Pick widely-used tools (TypeScript, Preact, Zustand) + thorough docs |
| Data loss during migration | Extensive testing, data validation, rollback plan |

## Conclusion

The web UI is **functionally complete but architecturally unstable**. It's a textbook example of "vibe coding" — code that works but violates nearly every modern best practice. The system works today because the complexity is manageable, but it will become increasingly painful to maintain and extend.

The modernization path is clear and achievable with incremental migration. By adopting standard tooling, establishing proper architecture, and adding tests, the project can reach production-grade quality without a dangerous full rewrite.

**Start with Phase 1** (tooling). Once Vite, TypeScript, and testing are in place, the rest becomes much easier.
